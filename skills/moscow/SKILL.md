# MoSCoW

Разложи элементы по необходимости для одной цели. Слот промпта — одна цель и один набор элементов: требования, задачи, функции или инициативы. Набор без цели и несколько несвязанных наборов слотом не являются.

Категория отвечает на вопрос, что будет, если элемент не делать. Must Have без этого элемента цель недостижима. Should Have заметно улучшает результат, и его можно отложить. Could Have — реальное улучшение, без которого результат остаётся полноценным. Won't Have (this time) сознательно остаётся за текущим объёмом.

## Куда писать

`.rdd/moscow/<набор>.md`

Один файл на одну цель. Имя файла — kebab-case цели: нижний регистр, слова через дефис, латиница (`Запуск оплаты` → `zapusk-oplaty.md`). Каталог создавай вместе с первым файлом. Повторный запуск для той же цели обновляет этот файл. Если в файле стоит `> пробел:`, продолжи с этого места. Сначала прочитай каталог: та же цель под другим написанием имени — обновляй его, второй файл не создавай. В файле уже другая цель — задай один вопрос и остановись. Каталог `.rdd/` коммитится вместе с репозиторием.

Язык файла — язык, на котором названа цель. Заголовки блоков и имена категорий оставь как в формате.

## Ход

1. Возьми цель и элементы из сообщения пользователя. Цель в сообщении не названа — прочитай её из приложенных материалов. Оттуда она не читается — задай один вопрос, какой результат должен получиться, и остановись до ответа. Элементов нет — задай один вопрос, что раскладываем, и остановись. Названо несколько несвязанных наборов — задай один вопрос, какой берём, и остановись. Цель не названа отдельным именем — имя файла возьми из формулировки цели. Готово, когда есть одна цель, список элементов и имя файла в kebab-case.

2. Прочитай репозиторий и `.rdd/` на опору цели: ограничения по времени и ресурсам, обязательные требования, зависимости, последствия отсутствия элемента. Готово, когда каждый заимствованный факт указан путём к файлу либо в репозитории опоры не нашлось.

3. Запиши контекст. Объём — что именно раскладывается. Ограничения — время, ресурсы и прочие условия из источников. Контекст приоритизации — релиз, проект, продукт или другое слово пользователя. Статус — слово пользователя: Draft, Reviewed или Finalized. Слова нет — Draft. Поля, которого нет в источниках, — `> пробел: что неизвестно; почему это меняет категорию; откуда взять ответ`. Готово, когда цель, объём и каждое названное ограничение записаны с опорой либо как пробел.

4. Назначь каждому элементу одну категорию по последствию исключения. Последствие бери из источников. Читай там влияние на цель, критичность для пользователей, обязательные требования, закон и технику, есть ли другой способ получить результат, зависимости. В обосновании остаётся то, что ответило на вопрос исключения для этого элемента. Проверь по порядку. Полностью убрать элемент — цель недостижима или результат неприемлем, и разумной альтернативы нет: Must Have. Иначе отложить элемент заметно ухудшает результат, а временный обход есть: Should Have. Иначе без элемента результат практически полноценный, и элемент — реальное улучшение: Could Have. Иначе в источниках есть причина сознательно не брать элемент сейчас — ценность против затрат, ресурсы, отсутствие нужды в этом контексте, риск или сложность, перенос на потом, несоответствие цели: Won't Have (this time), и эта причина записана. Последствие исключения в источниках не видно — категорию не ставь, на элементе `> пробел:`. Высокая ценность при ещё достижимой цели Must Have не делает. Готово, когда у каждого элемента одна категория и обоснование из источников либо пробел без категории.

5. Запиши связи. Отметь, где Must Have зависит от Should Have или Could Have, где исключение одного делает другой бесполезным, где элементы повторяют друг друга, где они противоречат, где элемент заменяется другим способом. Противоречие, которого контекст не разрешает, оставь открытым: категорию из-за него сам не меняй. Зависимости в источниках нет — у элемента строка `нет`. Готово, когда у каждого элемента строка зависимости заполнена или стоит `нет`, и каждое найденное противоречие записано без подмены категории.

6. Посчитай сводку. Число и доля каждой категории, доля — число этой категории, делённое на число всех элементов. Пустая категория остаётся в сводке с нулём. Минимальный объём — список Must Have. Дополнительная ценность — список Should Have. Вне текущего объёма — список Won't Have (this time). Риск распределения пиши, когда он уже следует из записанных связей или назван в источниках. Другой риск — `> пробел:`. Готово, когда доли сходятся с числами, сумма долей — все элементы, и пустая категория видна.

7. Запиши файл в формате ниже. Открытые вопросы собери из пробелов: что неизвестно, почему это меняет категорию, откуда взять ответ. Есть элемент без категории — в ответе один вопрос по первому такому элементу. Все элементы разложены, и осталось открытое противоречие — один вопрос по первому противоречию. Все элементы разложены, противоречий нет, и Must Have зависит от другой категории — один вопрос по первой такой связи. Готово, когда файл лежит по пути из первого раздела, а ответ называет этот путь, числа по категориям и остались ли элементы без категории.

## Формат файла

Один markdown-файл:

- заголовок `#` с целью;
- «Контекст» — цель, объём, ограничения, контекст приоритизации, статус;
- «Классификация» — по категориям Must Have, Should Have, Could Have, Won't Have (this time): элемент, обоснование, последствие исключения, зависимости;
- «Без категории» — элемент и `> пробел:`;
- «Сводка» — число и доля каждой категории, всего, минимальный объём, дополнительная ценность, вне текущего объёма, риски;
- «Связи» — зависимость, повтор, противоречие, другой способ; противоречие без разрешения так и помечено;
- «Открытые вопросы» — каждый пробел тремя частями: что неизвестно, почему это меняет категорию, откуда взять ответ.

Дырка в знаниях — цитата `> пробел:`. Пустая категория в сводке — ноль.

## Держать

- Категория говорит, что будет с целью, если элемент исключить.
- Must Have — без элемента цель этого контекста недостижима или результат неприемлем, и разумной альтернативы нет.
- Should Have заметно улучшает результат, временный обход назван, элемент можно отложить.
- Could Have — реальное улучшение, результат без него остаётся полноценным.
- Won't Have (this time) называет, почему элемента нет сейчас. Это не приговор навсегда.
- Зависимость записана на элементе. Противоречие остаётся открытым, пока его не разрешит пользователь.
- Доли получаются из числа элементов. Порядка выполнения категория не задаёт.
- В одном файле одна цель.
